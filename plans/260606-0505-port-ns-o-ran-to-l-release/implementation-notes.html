ns-O-RAN → OSC Near-RT RIC L-release — Implementation Notes

Running record of design decisions, deviations, tradeoffs, open questions. Plan: plans/260606-0505-port-ns-o-ran-to-l-release/ · Branch (superproject): dev/migrate-to-l-release · Started 2026-06-06.

1. Scope & Locked Decisions

  • Goal: Connect ns-3 RAN (ns3-mmwave-oran) to OSC L-release near-RT RIC. KPM-only this migration; E2SM-RC / closed-loop Traffic Steering deferred.
  • Version jump: E2AP v01.00→v03.01, E2SM-KPM v02.00.03→v03.00; PER→APER; TimeStamp 4→8 bytes.
  • e2sim: rebase oran-e2sim onto OSC e2-interface da6f82f2; re-apply ns-3 bits as adapter layer in oran-interface/model/ (public E2Termination API kept stable).
  • Topology: ns-3 co-located on the L-release VM, connects to E2Term node-IP:32222 (NodePort SCTP). No cross-VM routing.
  • Validation: versioned, re-runnable M1–M6 harness (scripts/l-release-validation/), golden-pcap diff at every milestone.
  • VC: feature branch dev/l-release per fork (origin=our fork, upstream=original). No upstream PRs.

3c. Phase 2 — Standalone rebased e2sim (M1–M5, no ns-3) M1–M3 GREEN M4/M5 subscriber-gated

  • Vendoring decision (fork): chose (a) wholesale-vendor. Histories are disjoint (wineslab fork vs OSC gerrit; da6f82f2 not in our history) and tree layouts differ (OSC ships asn1c/, Dockerfile_kpm, files.txt). Replaced the fork's e2sim/ subtree wholesale with OSC da6f82f2:e2sim via git read-tree --prefix=e2sim/. Verified exact: staged e2sim tree SHA 2031409… == git rev-parse da6f82f2:e2sim. The wineslab develop branch is preserved (ns-3 extensions re-applied as adapter in P4/P6). Staged, NOT committed (orchestrator/user to approve).
  • asn1c not a build dep: the OSC e2sim/asn1c/ dir contains pre-generated ASN.1 .c/.h (committed) compiled via add_subdirectory(./asn1c) — the build does not run asn1c. Pin captured from the file banner: asn1c-0.9.29, source module e2ap-epd-v03.01.asn (confirms E2AP v03.01). "Never hand-edit generated C" is satisfied structurally (we vendor as-is).
  • Build (oran-kvm-2, g++ 13.1.0, pure CMake, libtool NOT needed): cmake .. && make package && cmake .. -DDEV_PKG=1 && make package → e2sim_1.0.0_amd64.deb + e2sim-dev; dpkg -i both (lib + headers to /usr/local). KPM app: stage kpm_e2sm/ + e2sim/asn1c as sibling, nlohmann-json3-dev → cmake .. && make. kpm_sim links libe2sim.a statically (matches the reference oransim:0.0.999). Self-built fresh (own build-lrelease dir), not reusing the testbed prebuilt.
  • M1–M3 GREEN vs live E2Term 6.0.6 (192.168.122.78:32222): self-built kpm_sim → SCTP established (M1), E2setupResponse (M2), RANfunctionsAccepted func 2 with no reject (M3). Structural diff vs golden = byte-identical (same E2setupReq/Resp, RANfunctionID 2 ×2, OID123, E2nodeComponentConfigAddition/Ack v3.01 IEs, no RANfunctionsRejected). Evidence: scripts/l-release-validation/captures/phase2-m1-m3-selfbuilt-setup.pcap.
  • M4/M5 BLOCKED (open decision Q4): the bundled kpm_sim is reactive-only — it registers a subscription callback then blocks on "Waiting for SCTP data"; indications flow only after an external RICsubscriptionRequest. No KPM xApp is deployed (ricxapp has only hw-go). Driving M4/M5 needs onboarding scp-kpimon/kpimon-go (RIC-cluster-modifying) and surfaces the Q3 func-id 2-vs-0 mismatch. Harness scripts m4/m5 accept a pre-captured pcap and assert; run-all.sh reports them NOT-RUN until a subscriber exists. Escalated to orchestrator.
  • Harness: scripts/l-release-validation/ — m1…m5, run-all.sh, assert-pcap.sh, common.sh, manifest.txt (pins e2sim da6f82f2, asn1c 0.9.29, e2term 6.0.6), README.md, captures/.
Harness gotchas baked in: (1) VM tshark 3.2.3 has NO E2AP dissector (tshark -G protocols | grep e2ap empty) — assert-pcap.sh auto-detects this and falls back to dissector-independent byte signatures on SCTP DATA payloads: E2setupResponse = 20 01 (successfulOutcome/id-E2setup), RICsubResponse = 20 08, RICindication = 00 05, RANfunctionsAccepted = IE 00 09, plus ASCII ORAN-E2SM-KPM/OID123. On a tshark 4.x host it uses the full -V decode. Same PASS/FAIL either way. (2) NodePort/IPVS SNAT intermittently drops the setup DATA from cni0 → capture_exchange retries (×3) until a DATA chunk is captured. (3) e2mgr shows DISCONNECTED after a run because the sim's timeout sends SCTP ABORT on exit — the wire pcap (not the REST status) is the source of truth for M1–M3.
