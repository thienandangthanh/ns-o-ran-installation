ns-O-RAN → OSC Near-RT RIC L-release — Implementation Notes

Running record of design decisions, deviations, tradeoffs, open questions. Plan: plans/260606-0505-port-ns-o-ran-to-l-release/ · Branch (superproject): dev/migrate-to-l-release · Started 2026-06-06.

1. Scope & Locked Decisions

  • Goal: Connect ns-3 RAN (ns3-mmwave-oran) to OSC L-release near-RT RIC. KPM-only this migration; E2SM-RC / closed-loop Traffic Steering deferred.
  • Version jump: E2AP v01.00→v03.01, E2SM-KPM v02.00.03→v03.00; PER→APER; TimeStamp 4→8 bytes.
  • e2sim: rebase oran-e2sim onto OSC e2-interface da6f82f2; re-apply ns-3 bits as adapter layer in oran-interface/model/ (public E2Termination API kept stable).
  • Topology: ns-3 co-located on the L-release VM, connects to E2Term node-IP:32222 (NodePort SCTP). No cross-VM routing.
  • Validation: versioned, re-runnable M1–M6 harness (scripts/l-release-validation/), golden-pcap diff at every milestone.
  • VC: feature branch dev/l-release per fork (origin=our fork, upstream=original). No upstream PRs.

Harness gotchas baked in: (1) VM tshark 3.2.3 has NO E2AP dissector (tshark -G protocols | grep e2ap empty) — assert-pcap.sh auto-detects this and falls back to dissector-independent byte signatures on SCTP DATA payloads: E2setupResponse = 20 01 (successfulOutcome/id-E2setup), RICsubResponse = 20 08, RICindication = 00 05, RANfunctionsAccepted = IE 00 09, plus ASCII ORAN-E2SM-KPM/OID123. On a tshark 4.x host it uses the full -V decode. Same PASS/FAIL either way. (2) NodePort/IPVS SNAT intermittently drops the setup DATA from cni0 → capture_exchange retries (×3) until a DATA chunk is captured. (3) e2mgr shows DISCONNECTED after a run because the sim's timeout sends SCTP ABORT on exit — the wire pcap (not the REST status) is the source of truth for M1–M3.

3d. Phase 3 — Port E2 Setup (area A SCTP + B E2AP): oran-interface → libe2sim relink M2 GREEN

  • Build approach: built a standalone minimal app oran-interface/examples/e2-setup-minimal.cc linked against the installed libe2sim (E2AP v3.01) + the vendored oran-e2sim/e2sim/asn1c/ C objects. No ns-3 dependency in the binary. CMakeLists lives at /tmp/ns3-e2-phase3/CMakeLists.txt (regenerable; recipe in handoff). Binary: /tmp/ns3-e2-phase3-build/e2-setup-minimal.
  • Why asn1c objects must be linked separately: libe2sim_shared.so was built with the asn1c object files as external linkage (not bundled). The static libe2sim.a similarly does not bundle them. Must supply asn1_objects from oran-e2sim/e2sim/asn1c/ — same pattern as kpm_sim.
  • run_loop() signature: installed lib exposes E2Sim::run_loop(int argc, char** argv) with argv[1]=IP, argv[2]=port. The oran-interface.cc on dev/l-release calls the wineslab-extended run_loop(string, uint16_t, ...) — that signature is absent from the installed lib. The minimal app bypasses E2Termination and calls E2Sim::run_loop directly; the ns-3 E2Termination::DoStart() adapter is deferred to Phase 6 (full ns3-mmwave-oran integration).
  • RAN function registration: e2sim.register_e2sm(2, desc) where desc is "ORAN-E2SM-KPM" (ASCII, 13 bytes). The run_loop hardcodes ranFunctionOId = "OID123" and ranFunctionRev = 2, so only the func id and descriptor buffer come from the caller.
  • M2 GREEN: e2-setup-minimal 192.168.122.78 32222 → SCTP connected, E2setupRequest sent (func 2 / OID123 / rev 2 / ORAN-E2SM-KPM, E2nodeComponentConfigAddition v3.01), received SETUP-RESPONSE-SUCCESS (60 bytes). Evidence pcap: scripts/l-release-validation/captures/phase3-m2-ns3-setup.pcap.
