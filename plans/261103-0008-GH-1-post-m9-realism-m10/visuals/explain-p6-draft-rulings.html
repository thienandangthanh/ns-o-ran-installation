What the P6 questions are asking you

The P6 draft checks every measurement name the en-gNB and eNB report against the 3GPP rulebook, and renames the ones whose numbers do not match. Four questions came out of that work, and the advisors found a fifth. P6 cannot be committed until you answer them.

The gist

P6 is a new, strict lint for the KPM metric map. A row may keep a 3GPP name such as TB.TotNbrDl only if a registry entry says which 3GPP clause defines it, and only if the number ns-3 reports really is what that clause counts. Any row that fails gets a vendor name such as ns3.du.macPdu. Its position and measId stay the same, so no byte on the wire changes; only the name changes.

The draft passes its own lint. Applying it raised four questions the plan did not settle (R1–R4). Five independent advisors (four kongming runs and one Codex run) answered them separately, and all five gave the same direction on all four. A debate between Codex and kongming then found a fifth question (Q5) and corrected three details.

Warning

Bottom line: these are your decisions, and nothing is committed until you answer

Recommended: R1 strict · R2 accept the renames · R3 fix outside M10 · R4 accept, widened to three more rows · Q5 count the forwarded X2 data. R1–R4 block the P6 commit. The analogy: the express depot's logbook

This is the same parcel service as on the P10 page. The main post office (the LTE eNB) stamps every parcel. The express depot (the NR en-gNB) delivers some of them by fast van. Each office keeps a logbook whose column names come from a national rulebook (3GPP TS 28.552 for 5G offices, 32.425 for LTE offices). Head office (kpimon and the TS xApp) reads the logbooks.

P6 is an inspector. For each column, the inspector asks two things: does the rulebook have this column, and does the clerk count what the rulebook says to count? If either answer is no, the column gets the depot's own private name. Nothing is crossed out; the same numbers sit under an honest heading.

R1 asks how strict the inspector should be. The depot's clerk counts the parcels a van delivered to each house. But when a house moves to another depot, its page is torn out before the clerk adds it up, so those parcels are never logged. Is a count that misses parcels at every move still "the rulebook's count"?

Note

Where the analogy stops

A real clerk could find the torn page. In ns-3 the count is lost for good, because RNTIs (the UE's number at the cell) are never reused. Also, the logbook goes to head office every 100 ms, not once a day.

R1: may a count that misses events keep its 3GPP name? (recommended: strict)

The question. Ledger row 147 says a 3GPP-named row must pass its value check ("the value check holds"), but it does not say what to do with known gaps. Should a gap that is written down still pass?

What is wrong with the TB counts. 3GPP TS 28.552 §5.1.1.7.1 and §5.1.1.7.3 (pp.111–112) count a TB "on transmission by the gNB of TB to UE". ns-3 counts each TB when the UE finishes receiving it and keeps the count per UE. Two paths lose TBs: - Gap 1. At an SN change, RemoveUe erases the UE (lte-enb-rrc.cc:5582-5612, 5892-5900) before the next report adds it up (mmwave-enb-net-device.cc:1152-1165). Up to one report period of that UE's TBs is never reported, and this happens at every handover the TS xApp triggers. - Gap 2. The UE PHY drops a TB whose cell ID does not match before it is traced (mmwave-spectrum-phy.cc:431-437).

Under strict, gNB cell TB.TotNbrDl(.1) and TB.TotNbrDlInitial become ns3.du.macPdu and ns3.du.macPduInitial. Their numbers stay exactly the same.

Strict (recommended)

  • A row keeps its 3GPP name only if every event the clause counts is counted exactly once, on every path the runs reach
  • Only timing may differ: ≤1 slot for counts, ≤1 of the clause's own sampling steps for sampled values. The 100 ms E2 report period never counts as a sampling step
  • This allowance is our project's tolerance, not a 3GPP number, and the amendment says so
  • A verdict is tied to the ns-3 pin and scenario config, and is re-judged when either changes
  • Matches your 20:46 precedent: RRU.PrbTotDl/Ul and TB.ErrTotalNbrDl were renamed because their values failed

Lenient (a disclosed gap passes)

  • Keeps two 3GPP names on the en-gNB, which stock xApps such as ad-cell expect
  • But any defect could then pass by being disclosed, so the value check could never fail
  • Reading "holds" as "holds except for gaps" after the check was registered narrows it, which the scope guard forbids (goal-packet.md, AC18)
  • The loss is a bias, not noise: it grows with the handover rate, which is exactly what the closed loop changes

Danger

Consequence of strict that the draft did not show: the eNB RRC.ConnMean is renamed too

The draft passes the eNB RRC.ConnMean by assuming that a UE context counted before it connects adds at most about one 10 ms sample. The source cannot prove that. LTE control-channel errors are on by default (lte-spectrum-phy.cc:222-225), so a random-access attempt that fails and times out after 15 ms (lte-enb-rrc.cc:3177-3184) is a live path, and scenario-zero traces no RRC state, so no run can show the bound. Under strict, the row becomes ns3.* until an instrumented run proves it. Net effect: until P9, no row in the map passes under a 3GPP name.

Background

Why not a numeric tolerance, such as "under 1 % lost"?

The static lint cannot measure it, the loss grows with handover rate × report period, and the threshold would be a spec choice nobody can source. The scope guard says to ask you rather than invent one.

Why the timing allowance is worded so carefully

If "one sampling interval" could mean the 100 ms E2 report period, then gap 1, which loses at most one report period per SN change, could be argued into an allowed timing shift. The wording blocks that. It also adds a boundary rule: each event really happens and is counted once, in the period that holds the code's counting instant.

What would change the recommendation

Run evidence that no judged run reaches an SN change on a cell whose TB rows are judged, or a 3GPP text that allows TB counts to omit events. Neither was found.

Q5 (new): does data forwarded between en-gNBs count over X2? (recommended: count it)

Why it is new. Your 19:52 ruling Q2 (ledger row 151) defines new X2 counters for P9 and excludes, with disclosure, the data the source en-gNB forwards to the target en-gNB during an SN change. Strict R1 turns that exclusion into a gap: P9's X2 rows could then never pass, and the empty pending list that row 147 (8) requires at P9 and P11 could never be reached.

In the analogy. When a house moves to a new depot, the old depot drives its undelivered parcels over the courier road to the new one. The rulebook column is "bits sent over the courier road". Do those parcels count?

What the text says. 28.552 §5.1.2.1.1.2 a) and c) (pp.183–184) count "bits transferred in the downlink through X2 interface", with no limit on which endpoints. ns-3 sends the forwarded data over X2 (lte-enb-rrc.cc:1213-1219, ForwardRlcPdu). The winning candidate had proposed calling the exclusion an "interpretation" based on Annex A.25 (p.403). Codex showed that Annex A is informative (p.397), and A.25 says only that MN–SN volume "should be counted". It exempts nothing, so that label would be a lenient pass under a new name. kongming accepted this challenge.

Warning

What could flip the recommendation (confidence: medium)

If so, ns-3's forwarding is a modelling shortcut, which favours (a).
